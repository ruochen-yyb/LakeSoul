# Presto 查询 LakeSoul CDC 表随版本累积变慢的分析与解决方案

> 分析时间：2026-08-13 15:52（Asia/Shanghai）
> 问题：LakeSoul 数据通过 Presto 查询，CDC 表每次更新产生一个新版本，时间越长查询越慢，是否有更好的方式？

## 结论

变慢是 **merge-on-read 架构的固有代价**：CDC 每次更新追加新文件，旧文件不删除，Presto 查询时需要打开并归并所有历史版本文件。文件数随时间线性增长，查询随之变慢。

**更好的方式 = 周期性 Compaction（合并版本）+ 过期版本/文件清理（Clean）**。LakeSoul 已内置这两套机制，无需新开发，只需部署配置。

## 变慢根因（数据流）

### 1. 写入侧：CDC upsert 是"追加式"提交

- Flink CDC sink 每次 checkpoint 提交 `AppendCommit`，文件全部 `FileOp.add`（见 [LakeSoulSinkCommitter.java](file:///e:/workspace/workspace/LakeSoul/lakesoul-flink/src/main/java/org/apache/flink/lakesoul/sink/committer/LakeSoulSinkCommitter.java) L150-158）。
- 同一主键的多个版本散布在不同 Parquet 文件中，元数据 `partition_info` 中版本（snapshot）持续累积。

### 2. 查询侧：Presto 走 native reader 的 merge-on-read

- [LakeSoulPageSource.java](file:///e:/workspace/workspace/LakeSoul/lakesoul-presto/src/main/java/com/facebook/presto/lakesoul/LakeSoulPageSource.java) L50-85：`NativeIOReader` 把 split 内**所有文件** `addFile`，`setPrimaryKeys` 后由 Rust 层做按主键的归并去重（LSM merge-on-read）。
- 代价随文件数增长：
  - 打开/读取的 Parquet 文件数线性增加（IO + footer 解析开销）；
  - 归并排序的数据量增大（同一 key 重复读取 N 个版本）；
  - 元数据快照膨胀 → split 生成变慢。

## 解决方案

### 方案一：Compaction（核心，必做）

将同一分区/桶内的多版本文件在 native 层合并重写为少量文件，查询时无需 merge，直接读。

LakeSoul 已提供三种触发方式（均位于 lakesoul-spark）：

| 方式 | 入口 | 说明 |
|---|---|---|
| 手动/定时 | `LakeSoulTable.compaction(condition, ...)` [LakeSoulTable.scala](file:///e:/workspace/workspace/LakeSoul/lakesoul-spark/src/main/scala/com/dmetasoul/lakesoul/tables/LakeSoulTable.scala#L316) | API 调用，可按分区条件增量合并 |
| SQL | `call lakesoul.system.compaction(...)`（CompactionCommand / CallExecCommand） | 适合调度系统（如 DolphinScheduler/Airflow 定时调 Spark SQL） |
| 常驻服务 | [NewCompactionTask.scala](file:///e:/workspace/workspace/LakeSoul/lakesoul-spark/src/main/scala/com/dmetasoul/lakesoul/spark/compaction/NewCompactionTask.scala) | PG `LISTEN/NOTIFY` 触发，支持 `file_num_limit`、`file_size_limit`、表白名单、线程池并发 |

建议配置：
- 按分区（如按天）调度 compaction，只合并"当日/近 N 小时"活跃分区，避免全表重写；
- 用 `file_num_limit` / `file_size_limit` 控制触发阈值（如单分区文件数 > 10 即合并）；
- CDC 高频表缩短合并周期（如每 10-30 分钟），低频表按小时/天。

注意：compaction 是写放大操作，安排在与 Presto 查询低峰错开的时段。

### 方案二：过期版本与废弃文件清理（配套，必做）

- Flink 侧 [NewCleanJob.java](file:///e:/workspace/workspace/LakeSoul/lakesoul-flink/src/main/java/org/apache/flink/lakesoul/entry/clean/NewCleanJob.java)：通过 PG CDC 监听 `partition_info` / `discard_compressed_file_info` / `table_info`，按 `data_expired_time` 清理过期版本快照和 compaction 废弃的旧文件。
- 必须部署运行，否则：
  - 元数据表持续膨胀，split 生成越来越慢；
  - compaction 标记废弃的旧文件残留磁盘，占用存储。
- 注意：`expired_time` 与 time travel（回滚/历史查询）需求冲突，按业务不需要回溯的时长设置。

### 方案三：写入侧减少版本/小文件（缓解，可选）

- 增大 Flink sink 的 `file_rolling_size` / `file_rolling_time`，降低 checkpoint 频率 → 每次提交文件更少更大；
- 上游 CDC 微批聚合（同一 key 多次变更合并为一次）减少无效版本。

### 方案四：查询侧兜底（可选）

- 对固定报表类高频查询，可用 Spark 周期物化一张"最新快照表"供 Presto 直查，彻底绕开 merge-on-read；
- 代价是数据时效性下降，适合 T+分钟级可容忍场景。

## 推荐组合

```
写入：Flink CDC sink（合理 rolling 参数）
        │
维护：NewCompactionTask（常驻，按阈值/分区合并）
      + NewCleanJob（常驻，清理过期版本与废弃文件）
        │
查询：Presto（merge-on-read，compaction 后大部分 split 只有 1 个文件，近似直接读）
```

预期效果：compaction 后每个分区/桶文件数从 N 降到 1，Presto 查询不再随时间退化，延迟趋于稳定。

## 不确定项 / 假设

- 未实测 compaction 后 Presto 的具体加速比，取决于文件累积程度与集群 IO；
- `NewCleanJob` 的参数默认值（如 ontimer 间隔单位换算）建议在部署前核对；
- Presto connector 是否有谓词下推/列裁剪的进一步优化空间，本次未深入评估。
