# Presto 查询非 CDC 表版本累积分析（对前文的补充与修正）

> 分析时间：2026-08-13 15:59（Asia/Shanghai）
> 问题：上一篇分析针对 CDC 表，若表不是 CDC 表，结论与方案是否变化？
> 关联文档：2026-08-13-1552-Presto查询CDC表版本累积变慢分析.md

## 结论

**核心结论与方案不变：只要是"主键 upsert 追加写"的表（无论是否 CDC），版本累积与 merge-on-read 变慢问题同样存在，Compaction + Clean 方案完全适用。**

但非 CDC 表内部要按"写入路径"细分三类，问题严重程度不同：

| 表类型 / 写入路径 | CommitOp | 快照行为 | 查询是否随时间退化 |
|---|---|---|---|
| 有主键 upsert 表（Flink 非 CDC 模式 / Spark upsert） | AppendCommit | 文件**追加**进快照 | **会退化**，与 CDC 表完全相同 |
| Spark SQL `UPDATE` / `DELETE` 更新的表 | UpdateCommit | 快照**整体替换**（copy-on-write） | 不退化，但写放大 |
| 无主键纯追加表（insertOnly） | AppendCommit | 追加 | 无版本归并开销，仅小文件增多导致轻度退化 |

## 依据

### 1. 元数据层：CommitOp 决定快照是"追加"还是"替换"

[metadata_client.rs](file:///e:/workspace/workspace/LakeSoul/rust/lakesoul-metadata/src/metadata_client.rs) `commit_data`（L456-548）：

- `AppendCommit | MergeCommit`（L457-504）：`snapshot.extend_from_slice(...)` —— 新文件**追加**到分区快照，旧文件保留 → 每次更新版本 +1、文件数累积。
- `CompactionCommit | UpdateCommit`（L506-548）：`cur_partition_info.snapshot = partition_info.snapshot.clone()` —— 用新文件集**整体替换**快照 → compaction 后每分区只剩合并后的文件；Spark `UPDATE` 也走此路径（重写受影响文件）。

这解释了 compaction 为什么有效：`CompactionCommit` 把累积的 N 个文件替换为 1 个，Presto 读取时无需 merge。

### 2. 非 CDC 主键表的写入路径仍然是追加

- Flink 非 CDC 模式：[LakeSoulTableSink.java](file:///e:/workspace/workspace/LakeSoul/lakesoul-flink/src/main/java/org/apache/flink/lakesoul/table/LakeSoulTableSink.java#L111-L120) `getChangelogMode`：`USE_CDC=false` 且有主键时返回 `INSERT + UPDATE_AFTER`，upsert 数据照样以 `AppendCommit` 追加新文件（committer 逻辑与 CDC 表相同）。
- Spark upsert（`UpsertCommand`）：同样走追加提交。
- 读取侧 Presto 不区分 CDC/非 CDC：`cdcColumn == null` 时只是不加 `!= delete` 过滤，**按主键 merge-on-read 的逻辑完全一样**（[LakeSoulPageSource.java](file:///e:/workspace/workspace/LakeSoul/lakesoul-presto/src/main/java/com/facebook/presto/lakesoul/LakeSoulPageSource.java#L69-L85)）。

### 3. Spark SQL `UPDATE`/`DELETE` 是例外

`UpdateCommand` 走 `UpdateCommit`：重写受影响文件并整体替换快照，不累积版本。代价是每次更新重写整个分区文件（写放大），更新频繁时写开销大，但 Presto 查询不退化。

## 针对方案的微调（相对上一篇）

1. **Compaction + Clean 方案原样适用**，无需改动；compaction 按主键合并，与是否 CDC 无关。
2. 先确认目标表的写入路径：
   - 若是 Flink/Spark **upsert 追加** → 必须配 compaction；
   - 若更新主要走 **Spark SQL UPDATE** → 查询不退化，无需 compaction，关注写放大即可；
   - 若是**无主键追加**表 → compaction 仅用于合并小文件（用 `file_num_limit` 触发即可）。
3. CDC 特有的 `!= delete` 过滤对非 CDC 表天然不存在，少一层过滤开销，可忽略。

## 数据流示意

```
非 CDC 主键表 upsert 写入（Flink / Spark）
   │  每次更新 → AppendCommit → snapshot 追加新文件（旧文件保留）
   ▼
Presto 查询：NativeIOReader addFile(全部文件) + setPrimaryKeys → merge-on-read
   │  文件数 N 随时间增长 → 查询线性变慢
   ▼
周期 Compaction：CompactionCommit → snapshot 整体替换为 1 个合并文件
   ▼
Presto 查询：单文件直读，延迟稳定
```
